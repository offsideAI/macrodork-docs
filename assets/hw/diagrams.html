01Where things live

The easiest thing to get wrong: the main board is not in the trunk, it is in the head. Camera, main board and HAT all belong to the same MJCF body, jaw_soft; the camera sits about 13 mm from the centre of the main board with no joint in between. The trunk cavity is almost entirely filled by the two hip-yaw servos, and the battery hangs outside, below the rear of the body.

02The battery feeds two rails; the servos run on raw battery voltage

This is the most counter-intuitive thing on the whole HAT: the servos are wired to raw battery voltage, with no step-down at all. The XL330 is officially rated 3.7–6.0 V, recommended 5.0 V, yet here it gets 6.6–8.2 V. That is not a typo; it is a deliberate upstream choice - more stall torque, paid for in heat and lifetime.

THIS EXPLAINS THE VOLTAGE ADAPTATION IN THE FIRMWARE

Because the servos run straight off the battery, the same command produces very different torque between a full and a flat pack. At runtime the compensation is scale × (7.4 / measured voltage EMA); without it the policy's behaviour drifts with the state of charge.

03Sixteen devices on one bus

This is the central argument of the whole design: 15 servos are daisy-chained on one three-wire bus, and the IMU also masquerades as a device on that bus. So the main board issues a single sync_read per cycle and gets body attitude and all 15 joint angles back together - timestamps aligned by construction, with no software juggling of jitter between two separate data paths.

THE 20 MS BUDGET IS TIGHTER THAN IT LOOKS

The XL330 ships with return_delay_time = 250, i.e. a 500 µs bus-turnaround delay per device. Quoting the source: "Across 16 devices that is 8 ms per tick — 40% of a 20 ms budget". The upstream fix is to write 0 to that register.

Whichever servo you switch to, this step has to be redone and measured - it is not one vendor's problem.

Why the detour is worth it: if the IMU were wired straight to the main board over I²C or SPI, attitude and joint angles would arrive over two different data paths, their sample instants would not line up, and a few milliseconds of jitter would contaminate the 61-dimensional observation directly. As a bus device, the problem does not exist at the hardware level.

WORKS WITH BOTH FEETECH AND THE STOCK SERVOS: NO HARDWARE CHANGE

The physical layers of the two protocols are identical - half-duplex single-wire TTL, 1 Mbps, three wires, 2.5 mm pitch connector. They differ only in packet format: Dynamixel V2 is FF FF FD 00 + CRC-16, Feetech STS/SCS is FF FF + inverted checksum.

So draw the hardware once and give the firmware two parsers; it can even listen on the bus at power-up and check whether the third byte is FD to detect the protocol automatically - plug in and go.

07Two routes: stock XL330 versus Feetech STS

The "IMU as the 16th device on the bus" architecture holds on Feetech too - because Feetech STS/SCS has its own bulk-read instruction, SYNC READ (0x82), used exactly the same way as on Dynamixel.

And the reply mechanism is the same on both sides. Protocol V2 does have a fast sync read (0x8A) that merges every reply into one packet, but the official runtime does not use it - a repo-wide search for fast_sync_read / 0x8A returns nothing, and duck-control/src/bus.rs:236 calls the plain sync_read_raw_data. This is also consistent with the "500 µs per device × 16 devices = 8 ms" in the source - if the replies were merged into one packet, the per-device delay would not be multiplied by 16.

UNEXPECTED FINDING: OUT OF THE BOX, FEETECH IS ACTUALLY AHEAD

Register 7 (0x07) of the STS memory map, Return Delay Time: default 0, with the note "Not functional on STS".

The XL330 ships at 250, i.e. 500 µs per device - quoting the upstream source: "Across 16 devices that is 8 ms per tick — 40% of a 20 ms budget" - and it has to be written to 0 by hand.

Since the reply mechanism is the same on both sides, this becomes the only substantive difference in the factory state - and it favours Feetech. Of course, writing a 0 on the XL330 side erases it, so this is not "Feetech is faster", it is "Feetech has one trap fewer".

ONE MORE REGISTER WORTH TUNING ON THE FEETECH SIDE

Register 8 (0x08) of the STS memory map, Response Level, default 1 - "reply to every command". Set it to 0 and only read and ping return a packet; ordinary write instructions no longer take up bus time.

This is the same kind of move as upstream writing 0 to return_delay_time on the XL330: the factory defaults are for general use; a high-rate control loop has to tune them itself.

ANOTHER QUESTION: DOES THIS HAT NEED TO BE BUILT AT ALL?

This is independent of which servo you pick; it is purely a cost call. The HAT is a 4-layer board with SMD assembly - prototyping starts at a few hundred yuan with a minimum order quantity - and roughly half the circuitry on it is audio (codec, amplifier, on-board microphone, speaker terminals).

If you are not doing voice features, that half of the board is wasted - in which case a bus adapter board costing twenty-odd yuan plus a buck module covers the two functions that are actually essential, "servo bus" and "power distribution", with the ToF hanging directly off i2c3. The price is losing on-board audio and Pi HAT+ identification.

DO THIS BEFORE DRAWING THE BOARD

The turnaround counts above are protocol facts, but converting them to milliseconds is an estimate. The real number depends on the tri-state buffer switching speed, the inter-packet gaps and the actual register length being read - only a measurement on real hardware will tell.

First thing once the servos arrive: connect a debug board, run both read methods, and time one full round of 16 devices. Until that number exists, the architectural decisions on the board are spinning in the void.
